\begin{abstract}
\noindent
Concurrency bugs in async JavaScript code often cause serious failures in
production systems.
Existing tools have two main weaknesses: rule-based detectors can spot
suspicious patterns but cannot suggest how to fix them, while large language
models (LLMs) can reason about code but tend to miss the exact line where
a bug occurs and require very large models (7B--32B parameters) to work well.
ThreadLearn addresses both weaknesses by combining a 5-pattern static race
detector with a small language model (Qwen2.5-Coder-1.5B) that is fine-tuned
using QLoRA (r=16, $\alpha$=32, 4-bit NF4 compression) on 783 training examples.
Each training example includes a step-by-step explanation written
\emph{after} the correct fix is already known (``hindsight'' reasoning).
At inference time, a BM25 keyword search retrieves the 3 most relevant
documents from a 2050-document knowledge base and adds them to the prompt.
On a hand-crafted benchmark of 20 JavaScript concurrency bugs across 8
categories, ThreadLearn with retrieval achieves a \textbf{75\% pass rate
(15/20)}, compared with 40\% (8/20) for the same model without fine-tuning
and 30\% (6/20) for GPT-3.5-turbo---a gain of $+$35 percentage points
over the base model and $+$45 pp over GPT-3.5.
The fine-tuning dataset (783 JSONL samples) and evaluation script
(\texttt{eval\_rag\_merged.py}) are publicly available.
\end{abstract}

\noindent\textbf{Keywords:} concurrency bugs, race conditions, static analysis,
LLM fine-tuning, Chain-of-Thought, JavaScript

\section{Introduction}
\label{sec:intro}

\subsection{Problem Statement}

Asynchronous JavaScript (Node.js) is widely used for building web backends,
but the language makes it easy to write code that behaves incorrectly when
multiple operations run at the same time.
A large-scale study (NodeCB~\cite{nodecb2017}) looked at 57 real concurrency
bugs in 53 open-source Node.js projects and found that 65\% involve two
operations conflicting on shared data (atomicity violations), 30\% involve
operations completing in the wrong order, and 93\% cause serious problems
such as crashes, wrong database values, or the program hanging.

Despite how common these bugs are, existing tools still fall short in
different ways.
Rule-based detectors can find suspicious patterns but cannot explain or fix
them, and they often produce false alarms on modern async/await code.
LLM-based tools can reason about whole functions but cannot pinpoint which
exact line caused the bug and need very large models to achieve good results.

\subsection{Gap Analysis}

We identify four concrete gaps in current tools:

\begin{description}[leftmargin=2em, labelwidth=2em]
  \item[\textbf{G1}] Rule-based detectors can only find bugs; they cannot fix them.
  \item[\textbf{G2}] PCWMs~\cite{pcwms2026} reaches 75.2\% accuracy but ignores
    the structural information from static analysis and needs 27K training samples
    with a large base model.
  \item[\textbf{G3}] No existing tool uses static analysis output as additional
    context to guide LLM reasoning.
  \item[\textbf{G4}] No end-to-end tool covers the full workflow of
    detect $\to$ explain $\to$ fix for JavaScript (Node.js).
\end{description}

\subsection{Key Insight}

The output of a static detector---which pattern was matched, on which lines,
and why it is dangerous---gives the LLM concrete, line-level evidence to
reason from, instead of guessing from general code patterns.
A small model (1.5B parameters) trained with this kind of grounded,
step-by-step reasoning outperforms a much larger model given only a
generic prompt, because it has learned to follow structured evidence
rather than surface-level text similarity.

\subsection{Contributions}

This paper makes four contributions:

\begin{enumerate}[leftmargin=2em]
  \item \textbf{\texttt{race\_detector}}: a 5-pattern static analyzer for
    JavaScript (Node.js) that works together with an AST code preprocessor
    (\S\ref{sec:design:detector}).
  \item \textbf{Hindsight CoT dataset}: a training dataset of
    \texttt{(code, detector\_output, reasoning\_trace, fix)} examples,
    where the reasoning is written with knowledge of the correct fix
    (\S\ref{sec:design:finetuning}).
  \item \textbf{ThreadLearn pipeline}: a complete system that detects,
    formats, retrieves context, and generates a fix, served via a FastAPI
    web endpoint (\S\ref{sec:design:pipeline}).
  \item \textbf{Evaluation}: comparison against NodeCB and PCWMs across
    fix pass rate, false-positive rate, and response latency
    (\S\ref{sec:eval}).
\end{enumerate}

\subsection{AST Preprocessing Foundation}

ThreadLearn's AST preprocessor provides four helper functions used by both
the race detector and the document retrieval stage.
AST (Abstract Syntax Tree) parsing converts raw source code into a structured
tree of named nodes---functions, variables, operators---so downstream tools
can work with precise code structure instead of plain text.

\paragraph{Example: closure loop variable (JavaScript).}
\mbox{}

\begin{lstlisting}[style=js, caption={Bug: \texttt{var i} is shared across all callbacks.}]
for (var i = 0; i < 5; i++) {
  setTimeout(function() {
    console.log(i); // always prints 5
  }, 100);
}
\end{lstlisting}

\begin{lstlisting}[style=js, caption={Fix: \texttt{let i} creates a separate copy for each loop iteration.}]
for (let i = 0; i < 5; i++) {
  setTimeout(function() {
    console.log(i); // prints 0, 1, 2, 3, 4
  }, 100);
}
\end{lstlisting}


\subsection{Hindsight Chain-of-Thought Fine-Tuning}
\label{sec:design:finetuning}

Inspired by PCWMs~\cite{pcwms2026}, we build training examples of the form:
\[
  (\textit{code},\; \textit{detector\_output},\; \textit{reasoning\_trace},\; \textit{fix})
\]
where \textit{detector\_output} is the structured report from the race
detector, and \textit{reasoning\_trace} is a step-by-step explanation
written by a teacher model \emph{after} the correct fix is already known.
Writing the reasoning in hindsight---starting from the answer and
explaining why it is right---produces cleaner, more consistent training
signal than asking a model to reason forward under uncertainty.

\begin{table}[ht]
  \centering
  \caption{Fine-tuning settings.}
  \label{tab:finetune}
  \begin{tabular}{@{}ll@{}}
    \toprule
    \textbf{Setting} & \textbf{Value} \\
    \midrule
    Base model         & Qwen2.5-Coder-1.5B \\
    Method             & QLoRA: $r$=16, $\alpha$=32, 4-bit NF4 weight compression \\
    Framework          & \texttt{SFTTrainer} (trl $\geq$ 1.5.0) \\
    Grounding input    & \texttt{pattern\_id} + \texttt{line\_range} from the detector \\
    \midrule
    \multicolumn{2}{@{}l@{}}{\textit{Rejected alternatives}} \\
    Full fine-tune     & Too expensive to run on available hardware \\
    Retrieval-only     & Finds relevant documents but cannot generate a fix \\
    \bottomrule
  \end{tabular}
\end{table}

\subsection{RAG-Augmented Fix Pipeline}
\label{sec:design:pipeline}

\begin{enumerate}[leftmargin=2em]
  \item \textbf{Extract keywords}: \texttt{ast\_preprocessor.extract\_keywords()}
    parses the input JavaScript using esprima, walks the syntax tree, and
    collects all \texttt{Identifier} tokens---function names, API calls,
    variable names---while skipping JS reserved words (\texttt{if},
    \texttt{const}, \texttt{async}, \ldots).
    The result is a list of up to 20 meaningful names used as a search query.
    Because the names are taken directly from the syntax tree, CamelCase
    names like \texttt{appendFile} and \texttt{setTimeout} stay intact
    instead of being split into separate words.
  \item \textbf{Retrieve documents}: BM25 scores the query against 2{,}050
    knowledge-base documents and returns the top-3 most relevant ones.
    Keeping API names intact means the query words match the document words
    exactly, giving better search results than a plain text tokenizer.
  \item \textbf{Format}: \texttt{report\_formatter} converts the
    \texttt{pattern\_id} into a human-readable severity label and a short
    fix hint.
  \item \textbf{Generate}: the fine-tuned LLM receives the 3 retrieved
    documents prepended to the prompt (using the same plain completion
    format as during training) and outputs the corrected code.
\end{enumerate}

\noindent\textbf{Why AST keyword extraction beats regex for search.}
A regex tokenizer splits \texttt{setTimeout} into \texttt{["set","timeout"]}
and \texttt{appendFile} into \texttt{["append","file"]}, creating a noisy
query where each word is too generic to find the right documents.
esprima reads the actual syntax tree and returns identifier tokens as-is,
so the search query contains the exact API names that appear in the knowledge
base---leading to more precise retrieval for JavaScript concurrency patterns.

produce any code on 3 tests.

\section{Conclusion}
\label{sec:conclusion}

Concurrency bugs remain a leading cause of failures in async JavaScript
applications, yet no existing tool both finds them and fixes them reliably
using a small model.
ThreadLearn combines a 5-pattern static race detector with a small language
model (Qwen2.5-Coder-1.5B) fine-tuned on step-by-step reasoning examples and
a BM25 document retrieval pipeline to deliver an end-to-end bug-fix system
for JavaScript (Node.js).
On a 20-case benchmark covering 8 bug categories, ThreadLearn with retrieval
achieves a \textbf{75\% pass rate (15/20)}, compared with 40\% for the
same model without fine-tuning and 30\% for GPT-3.5-turbo---a $+$35 pp
improvement showing that the right training format and domain-specific
fine-tuning significantly improve fix quality even at 1.5B parameters.

\paragraph{Future work.}
Expand to TypeScript AST (replace the current regex fallback);
add MPI/CUDA patterns (following PCWMs direction).
